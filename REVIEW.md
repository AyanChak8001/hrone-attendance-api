# REVIEW.md

The table below records defects identified in the starter implementation. The
status describes the current working implementation after the fixes.

| # | Where | Original behavior and impact | How to notice it | Current status / fix |
|---|---|---|---|---|
| 1 | Time helpers | Time values could be mixed between local, naive, and aware representations, and attendance-day calculations did not consistently apply IST or overnight rules. | A punch near midnight or an overnight shift receives the wrong date or derived values. | **Fixed.** Values are normalized to UTC at the MongoDB boundary, while attendance dates and shifts are calculated in IST. |
| 2 | Calculation helpers | Floating-point/banker-style rounding, missing overtime thresholds, and ordinary same-day shift-end logic produced incorrect derived values. | Boundary values such as 4.495 hours, exactly 30 minutes of overtime, or overnight shifts fail. | **Fixed.** Decimal half-up rounding, the 30-minute threshold, and overnight shift ends are implemented. |
| 3 | Employee creation and punch-in | Duplicate handling relied on check-then-insert behavior, and missing employees were not consistently converted to 404 responses. | Parallel duplicate requests race, or an unknown employee causes the wrong status or an exception. | **Fixed.** Unique indexes, duplicate-key handling, and explicit 404 responses are used. |
| 4 | Attendance listing and serialization | The starter could load and sort records in Python, expose MongoDB identifiers, and return BSON datetimes instead of API epoch milliseconds. | Large collections become slow and responses violate the contract. | **Fixed.** MongoDB performs filtering, sorting, pagination, and the API-boundary serializer removes `_id` and converts datetimes. |
| 5 | Health endpoint | Readiness could be reported without verifying that MongoDB answered. | The service reports healthy while MongoDB is unavailable. | **Fixed.** `/health` runs `ping` and returns 503 when it fails. |
| 6 | Department summary aggregation | `present_days` counted every presence-status record, including Saturday and Sunday records. R7 requires present days to count weekdays only. | A Saturday `PRESENT` record contributes 1 instead of 0 to the department total. | **Fixed.** The summary now applies the same weekday expression as employee-monthly analytics. |
| 7 | Department trend implementation | The starter aggregated existing logs, then filled missing dates and calculated the moving average in a Python loop. | The endpoint does not satisfy the database-side gap-filling requirement and does not scale with the requested dataset size. | **Fixed.** The current implementation uses MongoDB `$densify` and `$setWindowFields`. |
| 8 | Department trend input/query shape | The starter loaded all department employees into Python and constructed an `$in` filter for attendance logs. | Memory and query construction grow with department size, undermining the 100,000-record performance requirement. | **Fixed.** The current trend is built as a MongoDB pipeline with department/date lookups. Large-scale plan use still needs verification. |
| 9 | Explain endpoint | The starter returned simplified explain commands that did not match the real monthly, summary, leaderboard, or trend pipelines and did not preserve all endpoint behavior. | Explain output does not prove the actual endpoint query uses the intended indexes. | **Fixed.** The current endpoint reuses the real pipeline builders and sends MongoDB `executionStats` explains. In an isolated local run with 98,821 attendance records, no `COLLSCAN` stages were observed across the five explain targets. This is measured local evidence only; it is not an exact 100,000-record benchmark, a production performance guarantee, or a formal concurrent-load result. |
| 10 | Date validation | `date.fromisoformat()` accepted ISO date variants beyond the API's required `YYYY-MM-DD` representation. | Compact or week-date forms could be accepted even though the contract specifies `YYYY-MM-DD`. | **Fixed.** The shared `day()` helper now requires the exact `YYYY-MM-DD` shape before parsing, then rejects impossible calendar dates. |
| 11 | Month validation | The starter and current helper checked length and numeric month range but did not enforce a four-digit year with the documented `YYYY-MM` pattern. | A form such as `123-001` could pass the helper despite not matching `YYYY-MM`. | **Fixed.** `dates_for_month()` now requires `^\d{4}-(0[1-9]|1[0-2])$` before calculating the existing month boundaries. |
| 12 | MongoDB configuration fallback | The starter fell back to `mongodb://localhost:27017` and `attendance_db` when environment variables were absent. The assignment requires injected `MONGO_URI` and `MONGO_DB` values and prohibits hard-coded connection details. | Running without configuration silently targeted a local/default database. | **Fixed.** The application and seed script now require non-empty `MONGO_URI` and `MONGO_DB` values after loading `.env`, while process environment variables retain precedence. |

I did not treat PyMongo's naive UTC datetime return values as a separate defect:
the current implementation explicitly interprets naive values as UTC and removes
timezone information before BSON writes.
